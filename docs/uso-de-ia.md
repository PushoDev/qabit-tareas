# Uso de la IA

Herramienta: **Claude Code** (asistente de IA en la terminal), usada durante toda la prueba. Este registro se escribe sobre la marcha.

## Cómo se trabajó
Paso a paso: la IA propone y escribe un trozo pequeño, explica cada decisión, y el desarrollador lo revisa antes de seguir. Backend primero, frontend después.

## Registro

| Etapa | Qué se pidió | Qué se aceptó | Qué se corrigió o se rechazó |
|---|---|---|---|
| Preparación | Crear el proyecto (monorepo, instalación) y enlazarlo con el entorno local | Estructura `server/` + `web/`, scripts de arranque, proxy de `/api` | La IA instaló primero en un disco NTFS que perdía archivos; se detectó con una verificación y se movió al SSD. Una vez ejecutó `npm install` en la carpeta equivocada (sin daño; se revisó) |
| Git | — | — | Faltaba un `.gitignore` y se confirmó `node_modules`; lo detectó la IA al revisar lo que pegó el desarrollador y se corrigió antes de subir nada |
| Backend 01 | Base de datos, tipos y validación | `db.ts`, `schemas.ts`, `types.ts` con `CHECK` en la base y una sola fuente de estados | Verificado con un script de 9 casos y `tsc` antes de aceptar |
| Navegador | Revisar la API en Chrome | Hallazgos aceptados: el 404 devolvía HTML y la cabecera `x-powered-by` anunciaba Express | — |
| Backend 02 | Rutas, repositorio y manejador de errores | Capas ruta → repositorio, `createApp(db)`, formato de error único | Al probar, la IA vio que el id inválido decía el campo `(body)` y que «Required» salía en inglés: lo corrigió y repitió las pruebas. Un `pkill` mal escrito mató su propia terminal (error del comando, no del código) |
| Backend 03 | Tests del backend | 10 tests (Vitest + Supertest), base en memoria por test | Los 10 pasaron a la primera y la IA desconfió: rompió el código a propósito en 3 sitios (prueba de mutación) para comprobar que los tests fallan cuando deben, y luego restauró desde copia |
| Verificación con la base real | «Prueba la API y mira si llegan datos a la base» (idea del desarrollador) | Comprobación con peticiones reales y lectura directa del archivo SQLite; persistencia con un proceso nuevo | — (el desarrollador pidió esta verificación antes de pasar al frontend) |
| Frontend 01 | Tipos, cliente de la API y hook con estados de carga y error | `tasksApi`, `ApiError`, `useTasks` y 9 tests; protección contra la condición de carrera al cambiar de filtro | **Tropiezos de la IA:** (1) escribió `ApiError` con propiedades en el constructor y el proyecto lo prohibe (`erasableSyntaxOnly`): lo corrigió al ver el error de `tsc`; (2) al instalar Vitest 4, `npm` falló con un error interno; en los intentos de arreglarlo la IA **borró `node_modules` y tumbó los servidores del desarrollador** unos minutos (la base de datos quedó intacta). Se resolvió con `legacy-peer-deps` y se verificó con `npm ci` en copia limpia; (3) faltaba el peer `@testing-library/dom`. Tests verificados con prueba de mutación |
| Frontend 02 | Pantalla con lista, filtro, cambio de estado y estados de carga/error, y probarla en el navegador | 4 componentes y CSS con tema claro/oscuro; probado en Chrome real (filtros, PATCH, error simulado con reintento) | (1) El linter marcó `setState` dentro del efecto del hook: la IA lo reescribió derivando `loading`. (2) La pantalla salió en blanco: Vite había cacheado un módulo vacío porque se leyó mientras la IA reescribía el archivo; la IA lo diagnosticó mirando lo que servía Vite y lo resolvió con `touch`. (3) La IA modificó datos de ejemplo durante la prueba y los restauró |
| Frontend 03 | Formulario de creación validado, con los errores de la API bajo cada campo | `validation.ts` (función pura), `TaskForm` accesible, filtro que vuelve a «Todas» tras crear. Probado en Chrome con clics y teclado | La IA creó 2 tareas de prueba en la base de desarrollo y las borró al terminar (solo esas, por título). El caso «la API devuelve 400 con detalles» no se podía provocar desde la pantalla: se deja para un test de componente |
| Frontend 04 | Tests de componentes e integración (formulario con 400 y detalles, botón de estado, estados de la lista, validación, App) | 21 tests nuevos (30 en el frontend, 40 en total) y la prueba de mutación | Los 21 pasaron a la primera, así que la IA rompió el código en **6 sitios** a propósito y verificó que cada rotura la detecta un test distinto; luego restauró y comprobó que los archivos quedaban idénticos |
| Capturas | Idea del desarrollador: añadir capturas de pantalla «para que se vea profesional» | 4 capturas tomadas en Chrome real (lista, validación, filtro, error) y guardadas en `docs/img/` | La IA se equivocó de coordenadas en un clic (los mensajes de error habían movido el filtro) y repitió la captura pulsando el botón por su nombre. Creó 2 tareas de ejemplo para que la lista se viera variada y las borró después, sin tocar la tarea que el desarrollador había creado |
| GlowLine | El desarrollador aportó un componente de línea con resplandor (Tailwind) para separar el formulario del listado | Port a CSS plano con la misma API, 4 tests y uso entre formulario y listado | La IA **no instaló Tailwind** (no se usa en el proyecto) y explicó por qué; añadió `aria-hidden` y adaptó el núcleo al tema claro. Como las capturas ya no reflejaban la pantalla, las rehizo. Primero no veía el componente adjunto y se lo pidió al desarrollador antes de seguir |
| Contenedores | `compose.yaml` y Dockerfiles que funcionen con **Podman** (el desarrollador no usa Docker) y probarlos | Multi-etapa, usuario sin privilegios, volumen, nginx que reenvía `/api` | Al probarlo de verdad salieron **tres fallos**: el puerto 8081 estaba ocupado; tras reiniciar la API nginx daba 502 (IP cacheada); y un reinicio tardaba 10 s porque Node ignoraba `SIGTERM`. La IA los diagnosticó con los logs y las IP reales y los corrigió, y repitió la prueba. Su primera medida de recuperación usó la configuración antigua (podman-compose no recreó los contenedores): lo detectó y repitió con `down` + `up` |
| Colores (`NeonCard`) | El desarrollador aportó un componente (Next.js + Tailwind + framer-motion) para clasificar las tareas por colores | Port a CSS plano con el mismo API; colores por estado en un solo archivo; punto de color en el filtro; 8 tests | La IA **señaló defectos del original** (devuelve `null` al montar, `useState` en cada movimiento del ratón, partículas con posiciones aleatorias recalculadas en cada render, un `rgba()` con un color hex inválido) y los corrigió o quitó, en vez de copiarlos |
| Notificaciones | Notificaciones para los estados de las tareas «desde que se crean hasta el final» | Sistema `toast` propio (API de `show/update/dismiss`), eventos como funciones puras y 22 tests | El componente `Notification` real **no venía incluido** (solo la página de demostración): la IA lo dijo y construyó el sistema desde la API. El linter marcó un archivo que exportaba componente y hook: se separó. Quitó el «Tarea creada» del formulario por redundante. 7 roturas a propósito, 7 detectadas |
| Datos de ejemplo | Que la base tenga datos cuando otros descarguen el repo | `seed.ts`: solo con la tabla vacía, idempotente, en transacción; `SEED_DEMO=false` | Verificado desde cero, en local y con contenedores. Las capturas se rehicieron desde la instalación limpia para que el README muestre lo mismo que verá el revisor |
| Banner | Añadir `gestor-tareas.webp` al README y al proyecto | Copia con fondo oscuro (el original era transparente y se perdía en el tema claro) | La IA **advirtió que es una ilustración, no una captura** (muestra menú lateral y estadísticas que la app no tiene) y la etiquetó así |
| Vercel | «¿Podemos subirlo a Vercel?» y luego «los dos en una sola URL, no creo que entren muchos usuarios» | Función `api/index.mjs` + `vercel.json` + aviso de demo; SQLite temporal en `/tmp` | La IA **objetó que el tráfico no era el problema** (la persistencia sí: una instancia puede reciclarse) y ofreció alternativas con su coste; el desarrollador eligió la opción simple. Sugirió una **rama aparte** para no tocar lo entregado y declaró lo que **no pudo verificar en local** (el empaquetado del binario nativo en Vercel) |
